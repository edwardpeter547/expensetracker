# Release Engineering

**Status:** Proposed. Backend and mobile are not yet independently versioned in code (both `package.json` files are `1.0.0`), and no images or mobile binaries have been published.

## 1. Version model

The following identifiers are distinct and must not be conflated:

| Identifier | Purpose | Example |
| --- | --- | --- |
| Backend application version | Backend release | `1.4.0` |
| Mobile application version | Mobile release | `1.2.0` |
| API contract version | Compatibility between backend and mobile | `1` (or OpenAPI `info.version`) |
| CI build identifier | Traceability within CI | `github.run_id` / `run_attempt` |
| Git commit SHA | Artifact identity | `6c3ed0b…` |
| Docker image digest | Deploy identity | `sha256:…` |
| Android `versionCode` | Store counter | `42` |
| iOS `buildNumber` | Store counter | `42` |
| EAS build ID | Mobile artifact traceability | EAS-provided |
| GitHub Release version | Release documentation | component tag |

### Independent backend and mobile versions (preferred)

Backend and mobile are versioned independently because they release at different cadences and for different reasons. A mobile release does not force a backend bump and vice versa. Compatibility is tracked through the **API contract**, not through equal package versions.

### Component-specific tag convention

One repository tag must not version both applications. Use unambiguous component tags:

```text
backend/v1.4.0
mobile/v1.2.0
```

Release automation must be configured to emit these tags; tooling defaults (for example Release Please's `backend-v1.4.0` separator) must be verified and adjusted.

## 2. Semantic Versioning

Official releases use `MAJOR.MINOR.PATCH`:

| Change | Meaning |
| --- | --- |
| Major | Breaking API/behavior change; coordinated migration |
| Minor | Backward-compatible feature |
| Patch | Backward-compatible fix / hotfix |
| Prerelease | `-alpha.N`, `-beta.N` |
| Release candidate | `-rc.N` |
| Hotfix | Patch on a release tag, merged back to `develop` |
| Development build | Identified by commit SHA/build number, **not** a public version bump |

Not every merge to `develop` increments a public version. Official versions are assigned at release approval; `develop` carries development builds tagged by commit.

## 3. Release automation

Adopt **Conventional Commits** for messages and **Release Please** (or an equivalent release tool) to derive changelogs and component version bumps, gated by human approval of the generated release PR. Manual release PRs are an acceptable initial fallback but must still record the version in the release manifest.

Independent releases in one repository work by configuring Release Please for **two component paths** (`src/backend/**` and `src/mobile/**`) with distinct tag prefixes. A single repository tag never versions both components.

## 4. Build number generation

| Identifier | Source | Notes |
| --- | --- | --- |
| GitHub run ID / attempt | `github.run_id`, `github.run_attempt` | CI traceability only; never a store counter |
| Backend build number | run ID or a derived counter | Recorded in OCI labels |
| Android `versionCode` | EAS remote versioning | Monotonic integer, store requirement |
| iOS `buildNumber` | EAS remote versioning | Monotonic integer, store requirement |
| EAS build ID | EAS-provided | Mobile artifact traceability |

GitHub run numbers are convenient CI references but are **not** Android/iOS store counters. Store counters are owned by EAS remote version management (`remoteVersionSource`), synchronized to the current store value at adoption, and surfaced in release metadata. Concurrent builds are deduplicated/canceled so counters do not collide.

## 5. Docker image tagging and identity

Docker Hub is the intended registry (issue #6; repository name reported as `edwardpeter547/expensetracker`, unverified without credentials).

| Tag | Mutability | Meaning |
| --- | --- | --- |
| `sha-<sha>` | Immutable by convention | Build of an exact commit |
| `1.2.0` (component release) | Immutable by convention | Official release |
| `develop` | Mutable | Convenience pointer to latest merged development build |
| `latest` | Mutable | Latest official release only |

**Deploy by image digest** (`<repo>@sha256:<digest>`). A Docker tag alone is not guaranteed immutable unless overwrite prevention is enforced operationally or through registry controls; the digest is the deploy identity.

### OCI labels and provenance

Every image records source repository, commit SHA, build number, semantic version (on release), build timestamp, and workflow run URL. Build provenance and (when tooling is available) signed attestations are generated by the build job and stored with release metadata.

### Retention, promotion, rollback

Retain immutable release tags per a documented policy; prune old `sha-*` development builds on a schedule. "Promotion" is reuse of the exact digest across environments, never a rebuild. Rollback redeploys a previously recorded digest.

### Authentication

Docker Hub credentials live in environment-scoped GitHub secrets and are used only by trusted publish/deploy jobs. Credentials are never embedded in images, Dockerfiles, or workflow files.

## 6. API compatibility policy

Mobile users may run older installed versions, so the API must evolve compatibly. OpenAPI's `info.version` is **not** an automatic runtime compatibility guarantee; routing and guarantees are separate concerns.

| Change | Policy |
| --- | --- |
| Backward-compatible addition | Allowed without a mobile release |
| Breaking change | Backend **major** version; coordinated migration |
| Deprecation | Documented with a deprecation window before removal |
| Minimum supported mobile version | Recorded in the release manifest |
| Compatibility testing | Contract tests plus a matrix of supported mobile versions |
| Emergency rollback | Backend-only redeploy of a prior digest; never reverts schema |
| Support window | Defined by product; recorded in release metadata |

Compatibility metadata (API contract version, minimum mobile version) is recorded in the release manifest and in OpenAPI metadata, but runtime enforcement lives in the API itself.

## 7. Release manifest

Each deployment/release records, as a generated CI artifact:

- Backend version and image digest.
- Backend commit SHA and build number.
- Mobile version, Android `versionCode`, iOS `buildNumber`, EAS build ID.
- API contract version and minimum compatible mobile version.
- Deployment environment and timestamp.
- CI run reference and workflow outcome.

The manifest is a **generated artifact** attached to the GitHub Release and archived as a deployment record; it is not a handwritten duplicate source of truth. Version bumps live in release tooling/changelogs, not in a manually edited file.
